# Internationalization (i18n)

The UI is translated with [`react-i18next`](https://react.i18next.com/) /
[`i18next`](https://www.i18next.com/), plus
[`i18next-browser-languagedetector`](https://github.com/i18next/i18next-browser-languageDetector)
for automatic language detection. Setup lives in `src/i18n/index.js` and is
imported once, as a side effect, at the top of `src/main.jsx` — before the
app renders — so translations are ready on first paint.

Currently supported: English (`en`, default/fallback) and Spanish (`es`).

## How language is chosen

1. **Explicit choice** (`localStorage['csim_language']`) — set whenever the
   user picks a language from the switcher in the top bar. Always wins if
   present.
2. **Browser language** (`navigator.language` / `navigator.languages`) — used
   the first time a user visits with no stored choice. Locales are matched on
   their base code (`es-AR`, `es-MX` → `es`) via `load: 'languageOnly'` and
   `detection.convertDetectedLanguage`; anything not in `SUPPORTED_LANGUAGES`
   falls back to English.

`<html lang>` is kept in sync automatically (`src/i18n/index.js` listens for
`i18next`'s `languageChanged` event) — no component needs to touch it.

## Adding a new string

1. Add the key to `src/i18n/locales/en.json`. Use nested, namespaced keys
   grouped by feature/component, not flat English sentences:

   ```json
   { "editor": { "runButton": "Run" } }
   ```

   `en.json` is the source of truth — every key that exists there must also
   exist in every other locale file.

2. Add the same key, translated, to `src/i18n/locales/es.json` (and any other
   locale files).

3. In the component, call the hook and use the key:

   ```jsx
   import { useTranslation } from 'react-i18next';

   const MyComponent = () => {
     const { t } = useTranslation();
     return <Button>{t('editor.runButton')}</Button>;
   };
   ```

4. **Interpolation** — pass values as a second argument, never concatenate
   translated strings:

   ```json
   { "errors.fileNotFound": "Couldn't find \"{{fileName}}\"" }
   ```

   ```jsx
   t('errors.fileNotFound', { fileName });
   ```

5. **Pluralization** — use i18next's `_one`/`_other` suffixes (or the plural
   forms a given locale needs) and pass `count`; don't branch on `count`
   yourself:

   ```json
   {
     "files.selectedCount_one": "{{count}} file selected",
     "files.selectedCount_other": "{{count}} files selected"
   }
   ```

   ```jsx
   t('files.selectedCount', { count });
   ```

6. **Dates/numbers** — format with `Intl` driven by the active locale, not a
   hardcoded format:

   ```jsx
   new Intl.DateTimeFormat(i18n.language).format(date);
   ```

## What NOT to translate

- Code typed into the Monaco editor, or any user-authored file content.
- Language/syntax identifiers (`python`, `java`, `cpp` as analysis-language
  values — these are technical identifiers read by the backend, not display
  text).
- Raw log/analysis output coming back from the CSIM backend.

Only the app's own chrome (labels, buttons, tooltips, aria-labels, dialogs,
menus, toasts, validation/error messages, empty states) goes through `t()`.

## A gotcha worth knowing: identifier strings vs. display strings

Watch for constants that get reused both as a **display label** and as an
**internal identifier** (Redux lookup keys, equality checks, object keys).
`EDITOR_TYPES.DUAL_EDITOR`/`BULK_EDITOR` used to be exactly this — the same
string `'Dual Editor'` doubled as both the tab's rendered label and the key
`TOOLBAR_BUTTONS` was indexed by. It's been decoupled: `EDITOR_TYPES` now
holds opaque ids (`'dual-editor'`/`'bulk-editor'`) used only for lookups, and
`CodeTabsHeader.jsx` renders the tab label from `t('editor.tabs.dual'/'bulk')`
independently. If you introduce a new constant like this, decouple it the
same way rather than translating the identifier in place — translating an
identifier that's also used for logic/equality will silently break that
logic the moment the active language changes.

## MUI's own built-in strings

Some MUI components ship their own English text independent of anything in
`src/i18n` — `TablePagination`'s "Rows per page" / "of" labels are the one
currently in use. These are localized separately, via `@mui/material/locale`
(already bundled with `@mui/material`, no extra dependency): `App.jsx` builds
the theme with `createTheme(darkTheme, MUI_LOCALES[i18n.resolvedLanguage])`,
where `MUI_LOCALES` maps our language codes to MUI's locale objects (`enUS`,
`esES`). If a future component pulls in another MUI piece with built-in text
(`DataGrid`, `DatePicker`, etc.), check whether `@mui/material/locale` (or
the relevant package's locale export) has an entry for each of
`SUPPORTED_LANGUAGES` and add it to `MUI_LOCALES`.

## Adding a third language

1. Create `src/i18n/locales/<code>.json` with every key from `en.json`,
   translated.
2. In `src/i18n/index.js`:
   - Import the new file.
   - Add `<code>` to `SUPPORTED_LANGUAGES`.
   - Add `<code>: { translation: <import> }` to the `resources` map.
3. Add a display name for it under `language.names.<code>` in **every**
   locale file (so the switcher can render "Français" while in English,
   Spanish, etc.).
4. In `App.jsx`, add `<code>: <muiLocale>` to `MUI_LOCALES` if
   `@mui/material/locale` exports one for that language (it covers most —
   check `node_modules/@mui/material/locale` if unsure).

Nothing else needs to change — the switcher renders from
`SUPPORTED_LANGUAGES` and `language.names`.

## Language switcher

`src/components/Layout/LanguageSwitcher.jsx` — an `IconButton` (translate
icon, badged with the active language code) that opens an MUI `Menu` listing
`SUPPORTED_LANGUAGES`. Selecting an item calls `i18n.changeLanguage(code)`,
which updates the UI immediately, persists to `localStorage`, and updates
`<html lang>` — no reload, no Redux involvement. It's rendered once, in
`MenuAppBar`.
